# A browser on a running server, 4 November 2026: sign-up to closing, and an industrial solution to commissioning

The server was built on this machine from an integration of three branches at ac507ab:
- locale (PR 52);
- sign-up and plans (PR 53);
- the industrial solution with Operations' acceptance (PR 51), with the fix below.

It was built `--no-default-features --features ops`, so ERP and Operations were its only apps. It ran against a
database of its own (`ferrum_e2e`, never `ferrum_dev`) with these settings:
- `FERRUM_BASE_DOMAIN=localhost`;
- `FERRUM_SIGNUP=open`, `FERRUM_SIGNUP_PLAN=free`;
- `FERRUM_PLANS` with `free` at 3 people, 100 MB of files and 100,000 assistant tokens a month;
- the development mailer, which keeps mail in the outbox.

The interfaces were Ferrum-Frontend main at c912b56 (PR 13 included). A person drove it in the desktop app's
browser pane at `accounts.localhost:5190` and the workspace's own `harbor-hotel.localhost:5190`.

## What it found besides the failure

- The usage panel did not refresh after closing, so it did not say the workspace was closed. Ferrum-Frontend's next PR refreshes it.
- A size of nothing read "0 byte". The same PR makes it "0 bytes".
- Adding a person in a closed workspace was refused by the people quota, not as read-only. User administration is not held by the read-only state. That was so before this work, and is left as it was.

## What it does not show

- A deployment, the image, more than one replica, mail that leaves the machine, or Compose or Kubernetes.
- A real device. The acceptance values were typed, as a person on site would type them.
- Apps other than ERP and Operations, which this build left out.
